# Android Robot Setup

## 1. Purpose

`android-robot/` is the third-round Android robot publisher. It joins backend as a robot, connects to LiveKit, publishes the Android camera, and displays received mock control messages.

It does not move real robot hardware.

## 2. Requirements

- Android robot or test phone running Android 8.1 / API 27 or newer.
- Android Studio, or Android SDK + Gradle.
- USB debugging enabled for local APK install.
- Backend configured with real LiveKit values.
- Web client running for visual verification.

## 3. Backend Configuration

Create local `backend/.env`:

```text
PORT=3001
CORS_ORIGIN=http://localhost:5173,http://127.0.0.1:5173,http://localhost:5174,http://127.0.0.1:5174
LIVEKIT_URL=wss://your-project.livekit.cloud
LIVEKIT_API_KEY=your-api-key
LIVEKIT_API_SECRET=your-api-secret
LIVEKIT_TOKEN_TTL=1h
MOCK_ROBOT_ONLINE=false
```

Do not commit `backend/.env`.

The Android app must never contain `LIVEKIT_API_KEY` or `LIVEKIT_API_SECRET`. It only calls backend `POST /api/robots/join` and uses the returned token.

## 4. Build Debug APK

### Option A: Android Studio

1. Install Android Studio.
2. Open Android Studio.
3. Choose `Open`.
4. Select this directory:

```text
android-robot/
```

5. Let Android Studio install or sync the Android Gradle Plugin and SDK components.
6. Open SDK Manager and install:
   - Android SDK Platform 35, or the compile SDK shown in `app/build.gradle`.
   - Android SDK Build-Tools.
   - Android SDK Platform-Tools.
7. Confirm the project sync succeeds.
8. Use `Build > Make Project` or `Build > Build Bundle(s) / APK(s) > Build APK(s)`.

### Option B: Command Line

From the project root:

```bash
cd android-robot
gradle assembleDebug
```

If a Gradle wrapper exists locally:

```bash
./gradlew assembleDebug
```

If `gradlew` is missing and system `gradle` is available, generate the wrapper from inside `android-robot/`:

```bash
cd android-robot
gradle wrapper
```

Then run:

```bash
./gradlew test
./gradlew assembleDebug
```

Do not hand-write `gradlew` or `gradle-wrapper.jar`. The wrapper should be generated by Gradle so the wrapper files and checksum match.

If neither Android Studio nor system Gradle is available, Android build is blocked until the Android toolchain is installed.

Expected output:

```text
android-robot/app/build/outputs/apk/debug/app-debug.apk
```

## 5. Install on Android 8.1 Robot

Connect the robot over USB and confirm it is visible:

```bash
adb devices
```

Install:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

If `adb` is not found, install Android SDK Platform-Tools through Android Studio SDK Manager and add it to `PATH`.

If the robot blocks installation, enable:

- Developer options.
- USB debugging.
- Install via USB, if the vendor ROM provides this setting.
- Unknown source installation for the test environment, if needed.

## 6. backendUrl

Do not enter `localhost` or `127.0.0.1` on the Android robot.

On Android, `localhost` means the robot itself, not your development computer.

Use one of these:

```text
http://<computer-LAN-IP>:3001
https://<public-backend-domain>
```

Examples:

```text
http://192.168.1.23:3001
https://surf-backend.example.com
```

For local testing:

1. Put the robot and computer on the same Wi-Fi or LAN.
2. Find the computer IP address.
3. Start backend on port `3001`.
4. Make sure the computer firewall allows inbound connections to port `3001`.

The Android manifest currently allows cleartext traffic for LAN debugging. Treat this as local-development support only.

For online deployment:

1. Use `https://<public-backend-domain>`.
2. Do not use a self-signed certificate unless the robot has been configured to trust it.
3. The app derives WebSocket as `wss://<public-backend-domain>/ws`.
4. Confirm the backend `/health` endpoint is reachable from the robot network.
5. Do not use `http://` online even though cleartext traffic is enabled for LAN debugging.

## 7. App Fields

Android app fields:

- `backendUrl`: backend base URL, for example `http://192.168.1.23:3001`.
- `robotId`: stable robot ID, for example `robot-001`.
- `roomName`: LiveKit/backend room name, for example `robot-room-001`.
- `Publish microphone audio`: optional, default off.

Tap `Join and publish camera`.

The app will:

1. Call `POST /api/robots/join`.
2. Open backend WebSocket `/ws`.
3. Connect to LiveKit if `tokenMode` is `livekit`.
4. Request camera permission.
5. Publish camera video.

## 8. Camera Permission

When Android asks for camera permission, tap Allow.

If permission is denied:

- Android app shows a permission-denied status.
- Camera publishing does not start.
- Web client will show `Waiting for robot video` if the robot is online, or `Robot offline` if the robot WebSocket is not connected.

To grant permission later:

1. Open Android Settings.
2. Find the SURF Robot app.
3. Open Permissions.
4. Allow Camera.
5. Reopen the app and tap Join again.

## 9. Camera Occupied by Vendor Software

Some robot vendor apps may keep the camera open.

Symptoms:

- Android app joins backend.
- LiveKit connection may succeed.
- Camera status shows open/publish failure.
- Web client stays on `Waiting for robot video`.

Checks:

- Close the vendor camera/navigation app.
- Reboot the robot if the camera driver is stuck.
- Verify no system preview or debug camera tool is running.
- Try another simple camera app to confirm the hardware works.

## 10. Web Verification

1. Start backend with real LiveKit config.
2. Start Web client:

```bash
cd web-client
npm run dev
```

3. Open `http://localhost:5173`.
4. Join the same `roomName` used by Android.
5. Confirm status:
   - backend connected
   - websocket connected
   - livekit connected
   - robot online
6. Confirm the Android camera appears in the RobotVideo area.

Expected placeholders:

- `Robot offline`: Android robot has not joined backend WebSocket.
- `Waiting for robot video`: Android robot is online but camera video is not published or not subscribed.
- Live video: Android robot camera track is published and subscribed.

## 11. Control Message Verification

1. Join Web client as `controller`.
2. Send Forward, Back, Left, Right, and Stop.
3. Android app should update `Last control message`.
4. Android app must not move real hardware.

Allowed command IDs:

```text
1002
1003
1000
```

Fourth-round implementation still uses `MockRobotControlAdapter` only.

## 12. Troubleshooting

`tokenMode` is `mock`:

- Backend is missing `LIVEKIT_URL`, `LIVEKIT_API_KEY`, or `LIVEKIT_API_SECRET`.
- Android will not publish camera to LiveKit in mock mode.

Backend join fails:

- `backendUrl` is wrong.
- Android and computer are not on the same network.
- Computer firewall blocks port `3001`.
- Backend is not running.
- Online `backendUrl` is not HTTPS.
- Android rejects a self-signed or invalid TLS certificate.

LiveKit connection fails:

- `LIVEKIT_URL` is wrong.
- Token expired.
- Device cannot reach LiveKit network.
- LiveKit project credentials are invalid.

Web does not show video:

- Android and Web joined different room names.
- Android camera permission was denied.
- Camera is occupied by another app.
- Robot identity/name does not contain `robot`.
- Web client is still connected with an old token; refresh and rejoin.

## 13. Safety Boundary

Do not connect this app to motor, navigation, or vendor SDK control in the fourth round.

Before real movement is added, create a separate hardware test checklist with:

- Manual emergency stop.
- Low-speed defaults.
- Clear test area.
- Human supervisor near the robot.
- Feature flag or build variant that keeps motion disabled by default.
