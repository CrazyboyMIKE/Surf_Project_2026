# Architecture

## 1. Fourth-Round Architecture

```text
Public Web Client
  | HTTP join/control APIs
  | WebSocket hello/chat/control messages
  | LiveKit subscribe to robot video
  v
Public Backend Server
  | in-memory room state
  | LiveKit token generation
  | WebSocket chat/control relay
  v
Public LiveKit Server / LiveKit Cloud
  ^ publishes Android camera video
  |
Android Robot App

Optional local simulator:

Robot Web Publisher
  | POST /api/robots/join
  | WebSocket hello
  | LiveKit browser camera publish
```

The backend never forwards raw video frames. Web and Android clients connect to LiveKit directly with short-lived tokens generated by the backend.

Fourth-round deployment requires public HTTPS/WSS in front of the backend and Web client.

Key separation:

- Backend room logic lives in `state/roomStore.ts`.
- WebSocket message handling lives in `ws/webSocketServer.ts`.
- Robot command whitelist and parameter validation live in `control/commandValidation.ts`.
- LiveKit token logic lives in `services/liveKitTokenService.ts`.
- Frontend HTTP calls live in `web-client/src/api.ts`.
- Frontend WebSocket handling lives in `web-client/src/useRoomSocket.ts`.
- Frontend LiveKit media handling lives in `web-client/src/useLiveKitRoom.ts`.
- Robot video rendering lives in `web-client/src/components/RobotVideo.tsx`.
- Android backend join calls live in `RobotJoinApi.kt`.
- Android LiveKit connection and camera publishing live in `LiveKitRobotClient.kt`.
- Android WebSocket control receiving lives in `RobotControlMessageHandler.kt`.
- Android hardware-facing control is abstracted behind `RobotControlAdapter.kt`; the current implementation is `MockRobotControlAdapter.kt`.

## 3. State Model

```ts
type Role = "robot" | "controller" | "viewer";

type Participant = {
  id: string;
  name: string;
  role: Role;
  connected: boolean;
};

type RoomState = {
  roomName: string;
  robotId?: string;
  robotOnline: boolean;
  participants: Map<string, Participant>;
  currentControllerId?: string;
};
```

Current storage is process memory only. Restarting backend clears all rooms, users, controller state, and robot online state.

## 4. Backend Responsibilities

- Validate JSON request bodies.
- Create and read room state.
- Assign viewer/controller roles.
- Enforce single-controller rule.
- Generate real LiveKit tokens when credentials are configured.
- Fall back to mock token mode when credentials are missing.
- Give Web users subscribe-only LiveKit tokens.
- Give robot clients LiveKit tokens with join, publish, and subscribe permission for the requested room.
- Accept WebSocket `hello`.
- Broadcast chat inside one room.
- Validate and mock relay robot control commands.
- Release controller role when controller WebSocket disconnects.
- Mark robot offline when robot WebSocket disconnects.
- Start in production with `npm run start` after build.
- Read `PORT`, `PUBLIC_BASE_URL`, `CORS_ORIGIN`, `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, and `NODE_ENV` from env.
- Log method, path, response status, and request duration without logging secrets.

## 5. LiveKit Token Rules

Backend reads:

```text
LIVEKIT_URL
LIVEKIT_API_KEY
LIVEKIT_API_SECRET
```

Rules:

- All three values must exist to use real LiveKit token mode.
- If any value is missing, backend returns mock tokens.
- The API secret is never returned to Web, Android, or robot publisher.
- Web users receive subscribe-only LiveKit permission.
- Robot clients receive publish permission.
- Robot identity is stable: `robot-${robotId}`.
- Token room grant is limited to the requested `roomName`.

## 6. Web Responsibilities

- Join room through backend.
- Display backend, WebSocket, LiveKit, robot, room, role, and controller state.
- Connect to LiveKit with backend-returned URL/token.
- Listen for remote participants and video tracks.
- Prefer remote participant identity/name containing `robot`.
- Render robot video track.
- Show `Robot offline` when backend says the robot is offline.
- Show `Waiting for robot video` when LiveKit is connected and the robot is online but no video track is subscribed.
- Send/receive chat through WebSocket.
- Disable robot control buttons unless current role is `controller`.
- Send only whitelisted command IDs from the control panel.
- Use `VITE_API_BASE_URL` for public backend HTTP calls.
- Use `VITE_WS_BASE_URL` for public backend WSS connections.
- Display WebSocket and LiveKit errors when public connections fail.

## 7. Android Robot Responsibilities

- Collect `backendUrl`, `robotId`, and `roomName` from the operator.
- Call backend `POST /api/robots/join`.
- Use the returned `liveKitUrl` and token to join LiveKit.
- Request camera permission before publishing.
- Publish Android camera video through LiveKit.
- Optionally publish microphone audio, default off.
- Open backend WebSocket `/ws` with the returned `participantId`.
- Display connection, camera, and control-message status.
- Handle permission denial and camera-open failure without crashing.
- Accept public `https://` backend URLs for online deployment.
- Derive `wss://.../ws` from an HTTPS backend URL.
- Keep `RobotControlAdapter` mock-only in the fourth round.

## 8. Robot Web Publisher Responsibilities

- Remain as an optional browser simulator.
- Join backend as robot through `POST /api/robots/join`.
- Open backend WebSocket `hello` as robot.
- Connect to LiveKit with robot token.
- Request local browser camera permission.
- Publish one camera video track.

## 9. Deployment Boundaries

Fourth-round deployment:

- Web client is static build output.
- Backend is a Node.js process behind a public HTTPS/WSS platform.
- LiveKit is LiveKit Cloud or a public LiveKit Server.
- Android robot uses public backend URL instead of LAN IP.
- No production domain is hard-coded in code.
- No secret is stored in Web or Android.

## 10. Mock Boundaries

Still mocked in round four:

- Real robot movement.
- Robot vendor SDK.
- MQTT or hardware control.
- `robot_control` execution.
- Persistent storage.
- Account/auth system.

Real in round four when configured:

- LiveKit token signing.
- Web LiveKit room connection.
- Android LiveKit room connection.
- Android camera video publishing.
- Web remote robot video rendering.
- Public backend WebSocket relay of chat and mock control messages.

## 11. Fifth-Round Direction

Fifth round should choose between deeper video calling and real robot control:

- For true video calls: add Web user microphone/camera publishing, robot-side audio output, echo handling, and explicit user consent.
- For real robot control: keep commands behind a feature flag, integrate vendor SDK or MQTT through a real `RobotControlAdapter`, and run a physical safety checklist.
- Add persistence only when room history or auth becomes necessary.
